# モーション図鑑 — Motion Zukan

UIが生き物のように動く、感覚のカタログ。

メニュー・検索ボックス・トグルといった定番コンポーネントに宿る「気持ちいい動き」
（スカッシュ&ストレッチ、オーバーシュート、モーフィング…）を採集して、
触って観察できる標本として収録した図鑑です。

## 起動

```bash
pnpm install
pnpm dev
```

`http://localhost:5173` で図鑑が開きます。

```bash
pnpm build    # 型チェック + 本番ビルド
pnpm preview  # ビルド結果の確認
```

No.108〜110 は、No.90〜107 の18種が**ずっと1つの前提の上に立っていた**ことを撃った回です。
その前提は「**台帳は据わっている**」——行は全部描かれ、集合は変わらず、順番も変わらない。
現在地はその上を読み手（No.105 では機械）が動く、というのが18種に共通の絵でした。

| No. | 外れる前提 | 台帳の側で起きること |
|---|---|---|
| 108 | 行は全部描かれている | 行は在るのに**描かれない**（畳まれた中） |
| 109 | 行の集合は変わらない | **末尾が伸び続ける**（現在地が行ではなく境界になる） |
| 110 | 行の順番は変わらない | **現在地の行そのものが動く**（並べ替え） |

共通の設計則は、**現在地は行の同一性で持て（No.97）——ただしそれは、行が「描かれる・在り続ける・
同じ場所に居る」の3つを台帳が保証しているあいだだけ。台帳がどれか1つを降りたら、担体は
"行の上"を離れて別のものへ持ち替わる。持ち替えを黙ると、読み手は現在地を失ったと読む**こと。

- **No.108 描かれない** → No.106 の答え（縁に方角）が使えません。**内側には方角が無い**（上でも下でもない）ので、方角ではなく**入れ物を名指す**。代弁するのはいちばん外側の閉じた親だけで、**段数は言わない**。畳んでも現在地は不変（`data-place` が `taskA1a` のまま）、開き直すと枠内 y も **0.0px** で戻る。対照（畳んだら親へ移す）は開き直しても戻らない
- **No.109 伸び続ける** → 「末尾に居る」は行ではなく**動く境界**なので、行 id で持つと1件増えるたび古くなります（**No.97 の答えが持つ先を失う**）。担体は最終行ではなく終端の境界線に置き、10件届いても枠内 y は **0.0px**。対照は `data-row-id` が10回とも変わる＝**現在地が動いたように見える**
- **No.110 並べ替わる** → 図鑑で初めて、**守るものが2つあって両方は守れない**場面。現在地を守れば周りが流れ、周りを守れば現在地が流れます。既定は現在地を守り（**0.0px** / 対照 **34.0px**）、順位は**数で言う**（`data-rank` 7→8、位置は1pxも動かない）

この回いちばんの収穫は **No.109 が出した「動いているものの子にしない」** です。
No.106 の「動いていないものを動きで語らない」を一段実装に降ろすと、これになります。
対照は末尾の**行**に印を置くので、担体が**いま湧いているその行の内側**に乗り、
行の scale アニメーションを親子関係で巻き込んで **2.4px 揺れます**。
境界の担体はどの行にも属さないので、行がどれだけ激しく湧いても構造的に巻き込まれません。
**担体の正しさは、気をつけて守るものではなく、置き場所で構造的に保証するもの。**

No.108 が同じことを別の角度から言いました。囲みと代弁の印の排他は `if/else` ではなく
**1つの探索関数の裏表**（根から辿って最初の閉じた祖先を返すか `null` か）で書けるので、
「両方が1のコマは0枚」は実測する前から**崩しようがない構造**になります。
受け渡しも同じで、**同じ1つの DOM 要素を生かしたまま translateY を書き換えるだけ**にすると、
「受け渡し中も個数は常に1」は実装の必然として出てきます（実測でも28フレーム全部で1個）。

No.110 は、この図鑑がずっと使ってきた補正のやり方に修正を出しました。
No.90・93・96 の流儀は **cubic-bezier を JS で数値評価し、独自のクロックで scrollTop を追う**もの
でしたが、CSS の transition が始まる時刻と `performance.now()` の起点はずれるので、
遷移中に数 px 揺れます——**規約が禁じている「同じ仕事をする2系統」を自分で作っていた**わけです。
直しは曲線を予測するのをやめ、**いまこのフレームで実際に描かれている transform を読んで
scrollTop を書く**こと。読みと書きが同一の rAF に閉じるので原理的にずれません。
**別の transition が動かす値は、予測するより、いま描いている値を読むほうが単純で頑健。**

企画の側の誤りも2つ出ました。ひとつは No.110 のクランプの帯が「先頭になりました」と
名乗っていたこと——クランプが起きるのは順位1のときだけではなく（実測では**順位2**で起きた）、
**順位を名乗ると帯が事実でないことを言う**。名乗る先を「台帳の上端」に変えました。
もうひとつは No.109 の帯を枠の**上**に置いていたこと。追従が外れた瞬間の現在地は
「いちばん上に見えている行」なので、帯が**読み手がいま読んでいる行そのものを覆って**いました。
`▾` が指すのと同じ下の縁へ移すと、覆う相手が変わるだけでなく、着地の向きも読めるようになります。

No.105〜107 は、No.90〜104 の15種が**口に出していなかった2つの前提**を撃った回です。
その2つは「**現在地を動かすのは読み手**」と「**現在地は見えている**」。
前者は主語が1人であることを、後者は現在地とそれを見る枠が同じものであることを暗に置いていました。

| No. | 外れるもの | 何が2つになるか |
|---|---|---|
| 105 | 動かしているのが読み手ではない | **主語**が2人（機械と読み手） |
| 106 | 現在地が枠の外にある | **事実**が2つ（現在地と、現在地の方角） |
| 107 | 枠が2つある | **窓**が2つ（現在地は1つのまま） |

共通の設計則は、**現在地は台帳のもの、見え方は枠のもの、動かす権利は主語のもの。
この3つを1つの担体・1つの状態に畳むと、必ずどれかが嘘になる**こと。

- **No.105 主語が2人** → 機械の現在地は**塗り**、読み手の現在地は**囲み**。実測で既定は別の行に2つ立ち、対照は担体を兼ねて読み手の選択を **768ms** で上書きします。そして**この標本だけは図鑑の基本イージング（ぷるん）を使ってはいけない**——塗りは時間そのものを写した担体なので、緩急を付けると時刻が嘘になります（線形性の残差 既定 **0.93%** / 対照 **64.7%**）
- **No.106 枠の外** → 端に寄せた印は現在地ではなく**方角**という別の事実。現在地は動いていない（読みかけの `offsetTop` は 40 サンプル全部で **408px の1値のみ**）ので、**担体は縦位置を1pxも動かさず、距離は数で名乗る**（枠内 y の偏差 **0.0px**、変わるのは `2行上→8行上` の文字だけ）
- **No.107 窓が2つ** → 囲みは**両方の窓に出る**（同じ事実の2つの像）。追いかけるのは頼まれた窓だけで、もう片方は **280→280** と1pxも動きません。そして**同じ瞬間に、2つの窓が同じ現在地について違うことを言ってよい**（窓Aは囲み、窓Bは `▼1行下`）——見え方は窓の事実だからです

この回いちばんの収穫は **No.106 が出した「動かすな」** です。モーション図鑑がここで出す答えは、
**動いていないものについては動きで語らない**こと。枠外に出た現在地について担体を動かして語ると、
読み手は「現在地が動いた」と読みます。動かしてよいのは枠を越える瞬間の受け渡し 140ms だけで、
その間も縦位置の偏差は **0.0px**（動くのは scale と opacity だけ）。
あわせて、閾値についての一般則も出ました——**閾値を持つなら、その閾値が読み手に見えるものであること**。
「行が完全に見えなくなったら」という1つの閾値は、実測でも行の下端 442px と 1px の狂いなく一致し、
しかも読み手は「見えなくなった」を自分の目で確認できます。

No.105 は実装の側から**状態遷移のバグが2段で出る**ことを教えました。「自分の操作か読み手の操作か」を

No.102〜104 は、No.90〜101 の12種が**ずっと1つの前提の上に立っていた**ことを撃った回です。

No.101 が「持っているが適用しない」と言えたのも行が時間で壊れないからでした。
**この前提には、3つの別々の外し方があります。**

| No. | 外し方 | 現在地の姿 |
|---|---|---|
| 102 | まだ何も指していない | **0個** |
| 103 | 指しているのが1点ではない | **幅がある（端が2つ）** |
| 104 | 指す先に行が無い | **担体が行でない（連続空間）** |

- **No.102 個数が0** → 「無い」は担体の不在では描けない（読み込み中・空の台帳と**同じ絵に潰れる**）。**名乗らせる**。そして出発地の無い最初の1つは移動ではないので、**湧かせる**（出現と移動を撃ち分ける）

- **No.104 行が無い** → 座標は No.97 が撃ったもの。**近傍の名前＋相対**で持ち、倍率で**基準が持ち替わる**ことを黙らない。倍率の不動点は**読み手が指した点**

共通の設計則は、**現在地を1つの値で持てたのは行という不変量に寄りかかっていたから。
個数が1でない／不変量が無い場面では、現在地は「値」ではなく「名前のあるものとの関係」で持ち、

この回でいちばんの収穫は No.103 から出ました。**「範囲を端点で持つ」は、識別子を捨てた実装ではない。**

**露骨に位置で持つ間違いより、正しく見える間違いのほうが遠くまで生き延びます。**

No.96〜98 は、No.90〜95 が現在地を**最後は座標で担保していた**ことを撃った回です。

- **No.97 座標に誤差0で戻れるのに、そこに居るのは別の行** → 戻り道が保存するのは座標ではなく**行**。台帳が変わったら、押される前に帯が**劣化を名乗る**

No.97 でこの回いちばんの収穫が出ました。対照（＝No.94 の実装のまま）で「元の位置へ戻る」を押すと、

既定は逆に `scrollTop` が保存値と -102px ずれ、着地行 id が一致します——**誤差が出るほうが正しさの証拠**です。

No.96 は企画の誤りを1つ暴きました。初稿の台帳（12行）では、対照の静止後の差が **0.0px** になります。

No.93〜95 は、その No.90〜92 が**黙って置いていた前提**を1つずつ崩した回です。

上で消えたのと下で消えたの、頼まれた移動と勝手な移動、手に属する現在地と状態に属する現在地、

読みかけの行がいったん浮いて、閉じきった瞬間に戻る——この標本がまさに否定したい体験を

No.90 の「実測できることと、見て分かることは別」のちょうど裏返しにあたります

No.90〜92 は**読み手の現在地**を3つ集めた回です。

現在地は3通りに壊れます——外から来たものにずらされる、遠くに溜まったものが読めなくなる、

No.87〜89 は**動きが届かないところ**を3つ集めた回です。

No.81〜83 は**動きが終わる前に、次の入力が来る**場面を3つ集めた回です。

- **No.82 同じ入力が連発する** → **合流**。拍は1つのまま、振幅だけが育つ（回数は数字にしない）

No.73〜75 は**図鑑の基本イージング（ぷるん）が意味の側から使えない場所**を3つ集めた回です。
図鑑は72種にわたって `cubic-bezier(0.34, 1.56, 0.64, 1)` の「行き過ぎて戻る」を共通語彙にしてきましたが、
この3か所ではそれが**使えないのではなく、使ってはいけない**——理由がそれぞれ違います。

- **No.73**：再生ヘッドをユーザーが握っている。予備動作を仕込むと、逆走したとき
  「これから起きること」の予告が「さっき起きたこと」の位置に出て意味が壊れる
- **No.74**：確度の帯が行き過ぎるのは「一瞬だけ実際より確信していた」という、確度についての嘘になる
- **No.75**：緩急そのものが状態（負債の残高）なので、跳ね方は演出ではなく情報になっている

代わりに何が気持ちよさと意味を作るか、が3種の中身です。No.73 は速度由来の誇張だけを使い
（逆走で符号が自然に反転するので対称に壊れない）、No.74 は幅の縮み方だけで語り、
No.75 は跳ね返りの量そのものを目盛りにしました。
No.75 は図鑑で初めて、**前の操作が次の操作の緩急を変える**標本でもあります
（他の74種は全部「その場の1回」で閉じている）。

No.13〜26 は「ゲーム」カテゴリ。ゲームUIの定番フィードバック
（被弾・報酬・成長・待ち時間・緊張・エラー）をCSSだけで演じる標本群です。

No.27〜32 はモバイルゲームの「指の操作」標本群。長押し・ドラッグ・スワイプ・
フリックといったジェスチャーそのものを主役に、入力の深さや勢いが
そのまま画面の手応えになる感触を Pointer Events + CSS で採集しています。
（マウスでもタッチでも同じように触れます）

No.33〜37 はカードスタックの標本群。[Amicro](https://github.com/Subhan-code/Amicro--Micro-transitions-)
のカードUIからスプリング定数・角度・オフセットを採取し、Motion のバネを
CSSのイージングに換算して移植したものです（基本バネ stiffness180/damping20/mass0.8
≒ `transform 0.55s cubic-bezier(0.34, 1.3, 0.64, 1)`）。

No.38〜49 は「アナリティクス」カテゴリ。ダッシュボードのグラフに
「発表の緩急」を持たせる標本群です。棒・折れ線・円弧・点・セル・面・帯・針・数字といった
グラフの部品に、にょきにょき／ひと筆書き／熱伝導／滴り／鼓動といった動きの性格を掛けています。

No.50〜54 は**実プロジェクト側から逆算して足した標本群**です。
経営シミュレーション（RUNWAY 78）のUIを部品単位で数え、「必要としているのに
図鑑に無い動き」を洗い出して作りました。共通するのは、報酬の祝祭でも汎用UIのぷるんでもなく、
**数字が意味を持つ画面で緩急を作るための語彙**という点です。

- **符号を色ではなく向きで語る**（No.50: 増は上へ生え、減は肩からぶら下がる）
- **総量が変わらない中での押し合い**（No.51 / No.54: 誰かが太れば必ず誰かがたわむ）
- **状態ではなく変化だけを鳴らす**（No.52: 越えている間ではなく、越えた瞬間に震える）
- **「選んだ」と「効いた」の間に予約という状態を置く**（No.53: 呼吸 → 押印 → 締め）

No.53 / No.54 は操作そのものが主役なので自己完結の対話標本、
No.50〜52 は下のアナリティクス標本と同じ props 駆動です。

No.55〜58 は同じ棚卸しの続きですが、**すでに苗床にあった種**から
「そのプロジェクトで実際に使う当てがある」ものを選んで育てたぶんです。
No.55 前週比矢印は前期比を出す全タイル、No.56 目標の差し替えは毎週入れ替わる焦点、
No.57 アンロックは解禁条件、No.58 打刻はイベントマーカーに当たります。
種を寝かせておくと、あとで「使う当て」のほうから採りに来られる——という運用の実例です。

No.59〜61 は**「まだ確定していないもの」をどう見せるか**でまとめた3種です。
図鑑にはこれまで「起きたこと」を伝える動きは揃っていましたが、
**これから起きること・まだ動きうること・残り時間**を伝える語彙がありませんでした。
3つに共通するのは、状態をラベルや色で説明せず、**動いているかどうかそのものを意味にした**点です。

- **揺れている＝まだ効いていない / 止まった＝確定した**（No.59: 発効の瞬間は減衰させず1拍で固定する）
- **呼吸の振幅＝確度の低さ**（No.60: 同じ数字でも、振れているほど危うい）
- **落ちる速さ＝焼ける速さ**（No.61: 残量ではなく速度が危機感を運ぶ。そして時間は買い戻せない）

いずれも「確定」を派手な祝祭では祝わず、**動きが止まること**で伝えます。

No.62〜64 は**「探索の語彙」**の標本群です。
この3種を企画した時点の58種でトリガーを数え直すと、ほぼ全部が離散イベント
（クリック・状態変化・データ到着）——つまり「何かが**起きた瞬間**」の語彙しかありませんでした。
けれど実際のダッシュボードで人がいちばん長くいるのは「見ている最中」、
カーソルを彷徨わせて数字を読んでいる時間です。この3種はその時間帯を受け持ちます。

3つに共通させた設計則は次の3点で、**イベント演出とは前提が違う**ところが要点です。

- **可逆であること** — 探索の動きは何十往復もするので「戻り」の緩急まで設計が要る。
  出は速く跳ね、戻りは少し遅く粘る。**戻りを跳ねさせない**（退場は主張しない）
- **主役は強調ではなく減衰で作る** — 触れたものを光らせるのではなく、それ以外を薄める。
  単色の図鑑では特にこれしか手がない。ただし No.64 が示すとおり、
  常時動く画面では**薄めても止めてはいけない**（止めた瞬間「主役でない」ではなく「死んでいる」に見える）
- **カーソルは連続、UIは離散** — 生の座標に追従させるとノイズになる。
  最寄りの意味単位（点・ピース・流路）へ吸着させ、乗り移りだけを補間する

実装上いちばん効いたのは、ホバー状態を `@keyframes` ではなく **`transition` で書く**ことでした。
探索の動きは最後まで再生されないのが常態（隣へ移ると前の動きは戻りきる前に引き返す）なので、
「いま居る場所から補間できる」ことが触り続けられる動きの条件になります。

なお No.63 は No.40 ドーナツの注ぎ込みと同じ部品ですが、**フェーズが違うので別標本**です。
No.40 は「登場」の語彙（弧が注がれて出来上がるまで）、No.63 は「探索」の語彙
（描き終わったあとに触る時間）。同じ部品でも、登場と探索には別々の動きが要ります。

No.65 / No.66 は No.50〜54 と同じ逆算（RUNWAY 78 の週報）から出た2種で、
**同じ場面に対する2通りの答え**として対になっています。

- **No.65 因果のリレー — 集計する側**。原因（投じた資源の配分）と結果（軸ごとの寄与）を
  上下に置き、原因どうしは直列・ひとつの原因が動かした結果は並列に動かします。
  並列に流すと「全部が同時に起きた」に戻ってしまうので、
  **直列と並列の使い分けそのもの**が伝える中身になっています
- **No.66 数値行の物差し — 集計しない側**。単位の違う数字を1つの図にまとめると
  「行をまたいだ長さは比べられない」という但し書きが要りますが、行ごとに物差しを
  持たせれば但し書きそのものが要らなくなります（満幅の意味が行の中で閉じるため）

実プロジェクト側で採用したのは No.66 のほうでした。集計した図は但し書きを1行足す代わりに、
「1枚しか動かしていない軸は必ず半分いっぱい」のような**読み手が知らなくていい約束**を
増やしてしまう——というのが実際に両方を実装して比べた結論です。

No.67〜69 は**「押した時点と、効いた時点のずれ」**の3種です。
それまでの66種はほぼ全部が「操作した瞬間に効く」を前提にしていて、
**操作と効果のあいだに時間が挟まる場面の語彙が1つもありませんでした**。
挟まり方は3通りしかないので、3種でその3通りを1つずつ受け持たせています。

| No. | ずれ方 | 効くのはいつ |
| --- | --- | --- |
| 67 | 効くのを遅らせる（取り消せる猶予） | 猶予が尽きたとき |
| 68 | 効くのが先の話（因果に潜伏期間がある） | 何週か先 |
| 69 | 効いたことにして先に見せる（楽観的更新） | もう効いている…はず |

3種に共通させた設計則は次の3点です。

- **待ち時間を進捗バーで語らない** — 残量ではなく「ほどける」「近づく」「たわむ」で言う。
  No.61（残りの砂）の「速度が量を語る」の続きで、ここでは**形が崩れていく量**と**距離**が時間を語る
- **未確定＝動いている / 確定＝止まる**（No.59〜61 の語彙の継承）。
  ただし **No.69 だけはこの則を意図的に破ります**（下記）
- **戻り道は往路と変える** — 取り消しや訂正を逆再生にすると「取り消した」ではなく
  「最初から何も起きていない」に見え、操作が届かなかったことにユーザーが気づけません。跡を残します

この3種で、図鑑の看板である `cubic-bezier(0.34, 1.56, 0.64, 1)`（ぷるん）が
**使えない場所**が2つはっきりしました。

**No.67 の猶予は linear で刻みます。** 猶予は物理ではなく契約なので、緩急を付けると
残り時間の読み取りが嘘になります（この標本にはオーバーシュートが一箇所もありません）。
あわせて、**ほどけの進行だけは CSS ではなく JS が持っています**。
グローバルCSSの `prefers-reduced-motion` は `animation-duration` を潰すので、
猶予の見た目を CSS アニメーションで書くと、動きを控える設定の人の画面では
**糸が一瞬でほどけ終わったのに確定だけが5秒後に来る**ことになります。
残り時間は装飾ではなく情報なので、減らす対象から外す——
No.61 で見つけた「常時アニメーションの reduced-motion 設計」の、もう一段先の話です。

**No.69 では「未確定＝揺れる」を破りました。** 楽観的更新の目的は待ちを消して
本当らしく見せることなので、未確定の合図を強く出したら本末転倒になります
（揺らした瞬間「失敗しそう」に見え、待たせているのと変わらなくなる）。
合図は縁の薄い破線と1px深い影だけに留め、呼吸は付けていません。
**約束を守るより、その約束が何のためだったかを優先した唯一の標本**です。

No.68 の主題は逆に「**押しても動かないことを、故障ではなく予告に見せる**」ことでした。
押した瞬間に何も動かさないと壊れて見えるので、線の代わりに別のもの——波紋と、
未来側ににじみ出るゴースト——を動かします。ゴーストの座標は、効いたあとに線が通る座標と
一致させてあります。だから到達の瞬間、影は消えるのではなく**線に吸われる**ように見えます。

No.70〜72 は**「向こう側にも時間が流れている」**の3種です。
69種を数え直すと、ほぼ全部が次の3つを前提にしていました——
①操作は1つずつ順に効く ②変化を起こすのは自分だけ ③確定した過去は動かない。
No.67〜69 は①を「ひとつの操作の行方」の範囲で崩しましたが、実装して見えたのは
**その前提自体が現実には保たない**ことでした。人は返事を待たずに次を押すし、
確定したはずの過去はあとから訂正されるし、画面を触っているのは自分ひとりではありません。
残っていた穴はちょうど3つで、1バッチで塞げます。

| No. | 崩す前提 | 一言 |
| --- | --- | --- |
| 70 | 操作は1つずつ効く | 自分の操作が**複数同時に**飛んでいる |
| 71 | 確定した過去は動かない | 時間の向きが**逆**のずれ |
| 72 | 起こすのは自分だけ | 変化を起こすのが**自分ではない** |

3種に共通させた設計則は次の3点です。

- **誰が起こしたかを、動きの強さで語る** — 自分の操作への応答はぷるん（0.28〜0.36s、振幅は大きくてよい）、
  向こうから届いた変化は跳ねない ease-out（0.50〜0.60s、振幅は半分以下）。
  「これは他人の変更です」とラベルで説明しません。図鑑の看板であるオーバーシュートは、
  この3種では**「自分が起こした」の印にだけ**使います
- **待ちと詰まりを長さで語らない**（No.61 / No.67 の継承）。進捗バー・待ち件数・スピナーではなく、
  たわみ・輪郭のズレ・追従の遅れで言う
- **消して差し替えない**（No.67 / No.69 の継承）。旧い値は輪郭やゴーストで 0.8〜0.9s 残す。
  読み手はもう旧い値を読んでいるので、跡が無いと「自分の記憶違い」に見えます

この3種でいちばんはっきりしたのは、**強弱の差そのものが「誰が」を語れる**ことでした。
No.72 は同じ画面に自分のホバー（0.3s のぷるん）と他者の書き換え（0.55s で跳ねない）を並べていますが、
名前も色も出していないのに、どちらが自分の操作かは見れば分かります。
モノクロ制約から「向き＝事実、濃さ＝評価」（No.55）が出たのと同じ筋で、
**主体を表す手段を全部封じると、緩急のほうが主体を語りはじめます**。

もうひとつの収穫は、**割り込みへの答えが2通りある**と分かったことです。
No.54（総量固定の配分）は入らないものを「断る」で答え、No.69 は保留中の再押下を首振りで断りました。
No.70 と No.72 はどちらも断りません——70 は溜めて列にし、72 は順番を譲って待たせます。
断るのは「これ以上は入らない」が本当のときだけで、**ただ順番の問題なら、断りは嘘**になります。

実物を見て直した企画の誤りが2つありました。どちらも仕様書の上では正しく、動かして初めて壊れる類です。

**No.71 の輪郭は前後関係を決め忘れていました。** 下方向の訂正しか頭になかったので背面に置きましたが、
上方向の訂正では旧い縁が新しい実体の「中」に来るため、塗りに飲まれて跡が消えます。
前面に出し、塗りの上に来るときだけ線の色を地の側へ反転させました
（跡が読めることを優先して色は変え、太さ・尺・消え方は変えていません）。

**No.72 のホバーは、強調のつもりが消失になっていました。** 持ち上がりと同時に地を一段暗くする実装で、
その色が図鑑カードの地（`#eaeae8`）とちょうど同じ。触った行だけが背景に溶けます。
持ち上がりは影で言い、地の色は変えない、に直しました。

アナリティクスの12種（No.38〜49）と No.50〜52 は**チャート本体を props 駆動の named export として切り出して**あり、
`data` や `value` が変わった瞬間（＝どんなトリガーでも）その規定値まで描画が走ります：

```tsx
import { SproutingBarsChart } from './specimens/bar-sprout'

// ボタンでも WebSocket でもスクロールでも、props が変われば描き直される
<SproutingBarsChart data={weekly} labels={days} replayKey={replay} />
```

図鑑に並んでいる default export は「その Chart を使う側の見本」で、
ボタンで規定値を差し替えるデモになっています。
ゼロから描き直す標本（棒・折れ線・ドーナツ・散布図・ヒートマップ・ファネル・収支の橋）は
同じデータでの再演用に `replayKey` を、現在値から新しい値へ滑らかに遷移する標本
（ゲージ・KPI・リング・エリア・レーダー・希薄化の帯・しきい値）は連続遷移を受け持ちます。

## 標本を連れて帰る（他プロジェクトでの活用）

アニメーションはすべて **依存ライブラリなしの CSS** です。
各標本は `src/specimens/<id>/` に自己完結しています：

```
src/specimens/toggle/
├── index.tsx   # 最小限の React 状態管理のみ
└── style.css   # 動きの本体。クラスは mz- プレフィックスで衝突しない
```

フォルダごとコピーして `import Toggle from './specimens/toggle'` するだけで動きます。
React 以外のプロジェクトでも、`style.css` のクラスとキーフレームはそのまま流用できます。

図鑑の詳細ビュー（カード右上の ⓘ）から各標本のソースコードを直接コピーすることもできます。

## 動きの設計メモ

- **緩急がキャラクターになる** — `cubic-bezier(0.34, 1.56, 0.64, 1)`（オーバーシュート）を基本のイージングとして共有し、ブランドとしての一貫した「ぷるん」を作る
- **予備動作 → 本動作** — 押すと一度潰れ、離すと跳ねる。溜めがあるから気持ちいい
- **変形は連続で** — ボタンがメニューに「なる」ことで、視線の迷子を防ぐ
- **二次アクションで生命感** — まばたき・呼吸・波紋など、主動作に添える小さな動き
- `prefers-reduced-motion` に配慮済み

## 新しい標本の追加

1. `pnpm new <id>` で `src/specimens/<id>/`（index.tsx + style.css）の雛形を生成（クラスは `mz-<id>-*`）
2. `src/registry.ts` の `specimens` 配列にメタデータ（名前・生態・動きの原理）を追記

これだけで図鑑に自動掲載され、ソースコード表示も効きます。

## 標本を収録する（PRに動く証拠を載せる）

動きの標本は静止画では良し悪しが判断できないので、GIF に収録する道具を置いてあります。

```bash
pnpm dev                                              # 別ターミナルで起こしておく
npm i --no-save playwright gifenc pngjs               # 収録用（package.json には入れない）
node tools/capture-specimen.mjs <id> out.gif
```

[`capture.html`](capture.html) が標本1種だけを 560×360 のステージに載せるので、
図鑑のヘッダーや他のカードが写り込みません。
ポインタの動かし方は [`tools/capture-specimen.mjs`](tools/capture-specimen.mjs) の
`CHOREO` に標本ごとに書きます——ホバーの標本は「どう触るか」が中身そのものなので、
撮り方を決めるのは説明を書くのとほとんど同じ作業になります。

図鑑本体の「依存ライブラリなし」を守るため、収録に要る3つは `package.json` に入れず
その場で入れて使います。

## アイデアの苗床（案出しと蓄積のしくみ）

完成した標本とは別に、**思いつきを貯める台帳**が [`src/ideas.ts`](src/ideas.ts) にあります。
1エントリ追記するだけで図鑑下部の「アイデアの苗床」セクションに自動で並び、
`seed（種）→ sprout（育成中）→ captured（標本化済み）` のライフサイクルで管理されます。

- 案出しのレシピ（部品 × 動きの性格 × ゲームの感情 の掛け算）
- 台帳への書き方と、種を標本に育てる手順

は [IDEAS.md](IDEAS.md) にまとめてあります。行き詰まったらそちらへ。
